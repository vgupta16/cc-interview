# Amenity Reservations

Residents of a building reserve shared amenities — party room, gym, guest parking — for a time
slot, without ever double-booking one, and without one building's bookings affecting another's.

This is a time-boxed slice, not a finished product. **[`DESIGN.md`](./DESIGN.md) is the main
document**: it covers the assumptions made, the questions a PM would need to answer, what was cut
and why, the data model, and the reasoning behind the concurrency design. The original brief is in
[`TASK.md`](./TASK.md).

## Prerequisites

- [.NET SDK 9.0+](https://dotnet.microsoft.com/download)
- [Node.js 20+](https://nodejs.org) and a package manager (`pnpm` recommended; `npm` works too)

## Run it (two terminals)

**1) Backend** → http://localhost:5080 (OpenAPI doc at `/openapi/v1.json`)

```bash
cd backend/Api
dotnet run
```

**2) Frontend** → http://localhost:5173

```bash
cd frontend
pnpm install
pnpm dev
```

Open http://localhost:5173. The Vite dev server proxies `/api/*` to the backend, so there's no
CORS to deal with. Data is in-memory: restarting the backend clears every booking.

### Try the interesting cases

Signed-in identity is a dev shim — use the picker in the top right to act as a different resident.

1. As **Riley Chen** (Harborview Tower), book the Party Room (Main) for 4:00–6:00 PM.
2. Try to book 5:30 PM on the same room — refused, with the conflicting window shown.
3. Book 6:00 PM instead — accepted, because a booking's end instant is free.
4. Switch to **Sam Okafor** (Maple Court) and book *their* party room for 4:00–6:00 PM — accepted.
   Different building, independent availability. Note the times shown are Central, not Eastern.
5. Back as Riley, book the Gym twice for overlapping windows (capacity 2), then a third — refused.

## Tests

```bash
dotnet test                 # from the repo root: 59 backend tests
cd frontend && pnpm test    # 24 tests over the pure frontend helpers
```

The backend suite includes concurrency tests that release a dozen threads at a barrier onto the
same slot and assert that exactly one — or exactly `Capacity` — wins. Those are the tests that
justify the locking design; see `DESIGN.md` §5.

## Regenerating the API client

The typed client in `frontend/src/api/generated/api.ts` is generated by orval from
`frontend/openapi.json`, a committed snapshot so a fresh clone works offline.

```bash
cd frontend
pnpm gen:api        # regenerate from the committed snapshot
pnpm gen:api:live   # refresh the snapshot from a running backend, then regenerate
```

Generated calls go through `src/api/http.ts`, which attaches the resident header and turns
non-2xx responses into a typed `ApiError`. `DESIGN.md` §9 explains why.

## API

All endpoints except `/health` and `/api/dev/residents` require an `X-Resident-Id` header, which
stands in for an authenticated session. The caller's building — never a value from the request —
scopes every operation.

| Method | Path | |
| --- | --- | --- |
| `GET` | `/api/amenities` | Amenities in the caller's building |
| `GET` | `/api/amenities/{amenityId}/reservations?fromUtc=&toUtc=` | Busy windows, plus the caller's own bookings |
| `GET` | `/api/reservations/mine` | The caller's active bookings |
| `POST` | `/api/reservations` | Book a slot |
| `POST` | `/api/reservations/{reservationId}/cancel` | Cancel your own booking |
| `GET` | `/api/dev/residents` | Dev-only roster for the identity picker |

Failures are RFC 9457 problem responses carrying a machine-readable `code` — `slot_unavailable`,
`exceeds_max_booking_length`, and so on — so the UI branches on the reason rather than the prose.
